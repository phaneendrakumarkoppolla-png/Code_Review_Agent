# When Code Review Needs a Memory

The hardest part of code review is not finding that a line is wrong. It
is remembering why the team decided to avoid that pattern in the first
place.

I wanted to build a code review agent that could do more than scan a new
piece of code for generic issues. The goal was to make the reviewer
aware of the development history around a project: previous review
comments, team conventions, recurring mistakes, and architectural
decisions. That led me to build a code review system around persistent
agent memory using Hindsight.

The interesting part was not simply connecting an LLM to a code diff.
The real engineering problem was deciding what the system should
remember, how it should retrieve that information, and how that context
should affect a new review.

## What the System Does

The system takes source code or a code change as input and produces a
structured review.

A conventional review flow looks roughly like this:

``` text
Code
  |
  v
AI Reviewer
  |
  v
Review Comments
```

That works for general programming mistakes, but it has an important
limitation: the reviewer starts from almost the same context every time.

My design adds a persistent memory layer:

``` text
                    +----------------------+
                    |   Previous Reviews   |
                    +----------+-----------+
                               |
                    +----------v-----------+
                    |  Persistent Memory   |
                    |      Hindsight       |
                    +----------+-----------+
                               |
New Code ---> Review Context ---> AI Reviewer
                               |
                               v
                         Review Results
                               |
                               v
                       Memory Retention
```

The important difference is that a completed review can become useful
context for a future review.

For example, suppose a team repeatedly decides that database access
should remain inside a service layer instead of being performed directly
inside controllers. A generic code reviewer may flag the architecture
inconsistently. A memory-aware reviewer can retrieve the team's earlier
decision and use it as part of the current review context.

## How the Pieces Fit Together

I separated the system into a few logical responsibilities rather than
putting everything into one large prompt.

The first responsibility is collecting the code and review information.

The second is retrieving relevant historical context.

The third is generating the review.

The fourth is retaining useful information from the completed review so
it can influence future work.

That separation matters because memory should not become a dumping
ground for every piece of text generated by the model. The useful
information is the information that can change a future engineering
decision.

The workflow is therefore:

``` text
1. Receive code
2. Identify the review context
3. Recall relevant historical information
4. Build the review prompt
5. Generate review findings
6. Present findings to the developer
7. Retain useful decisions and lessons
```

This also makes the system easier to debug. If a review is incorrect, I
can inspect whether the problem came from code analysis, memory
retrieval, prompt construction, or the generated response.

## Giving the Reviewer a Memory

The main technical idea is using Hindsight as the persistent memory
layer.

I used the Hindsight concept of recalling information that is relevant
to the current task and retaining useful information after the task is
completed. The official Hindsight documentation describes it as an agent
memory system designed to retain and recall information across
interactions.

[Hindsight GitHub](https://github.com/vectorize-io/hindsight)

[Hindsight Documentation](https://hindsight.vectorize.io/)

[Hindsight Agent Memory](https://vectorize.io/what-is-agent-memory)

The practical reason for using persistent memory is simple: the current
review should not have to rediscover every team decision from scratch.

A useful memory entry might represent a decision such as:

``` text
Decision:
Keep database queries inside the repository/service layer.

Reason:
Controllers should handle request-level concerns and should not contain
direct database access.

Source:
Previous code review and architectural discussion.
```

Later, when a new change introduces database access directly inside a
controller, the system can retrieve this context before generating its
review.

The model is then not relying only on general programming knowledge. It
also has project-specific context.

## The Review Flow

The review process can be thought of as two loops.

The first loop is the immediate review:

``` text
New Code
   |
   v
Recall Relevant Memory
   |
   v
Construct Context
   |
   v
Generate Review
```

The second loop updates the system's future knowledge:

``` text
Review
  |
  v
Identify Useful Decisions
  |
  v
Retain Memory
  |
  v
Future Reviews
```

That second loop is what makes the system different from a stateless
prompt-based reviewer.

Not every review comment needs to become permanent memory. Temporary
observations, duplicate comments, and irrelevant details can add noise.
The useful memories are things such as stable conventions, accepted
trade-offs, recurring defects, and architectural decisions.

## Code-Level Implementation

The application is structured around a backend that handles the review
workflow and a frontend that provides the developer-facing interface.

A simplified request handler follows the same general pattern:

``` javascript
app.post("/api/review", async (req, res) => {
  try {
    const { code } = req.body;

    const context = await recallRelevantMemory(code);

    const review = await generateReview({
      code,
      context
    });

    await retainReviewMemory(review);

    res.json({ review });
  } catch (error) {
    res.status(500).json({
      error: "Failed to review code"
    });
  }
});
```

The important detail here is the ordering.

The system recalls memory before generating the review. After the review
is produced, useful information can be retained for later requests.

The memory functions can remain isolated from the HTTP layer:

``` javascript
async function recallRelevantMemory(code) {
  // Query persistent memory for context related to this code.
}

async function retainReviewMemory(review) {
  // Store useful review decisions for future reviews.
}
```

This separation makes it possible to change the memory implementation
without rewriting the entire API.

The review generation step can then focus on combining the current code
with retrieved context:

``` javascript
const prompt = `
Review the following code.

Current code:
${code}

Relevant project memory:
${context}

Focus on correctness, maintainability,
security, and consistency with previous decisions.
`;
```

In a production implementation, I would keep the prompt construction
more structured and validate the returned review before sending it back
to the client.

## Why Persistent Memory Changes the Review

Consider a simple example.

A developer submits:

``` javascript
app.get("/users", async (req, res) => {
  const users = await db.query("SELECT * FROM users");
  res.json(users);
});
```

A generic reviewer might discuss SQL safety, error handling, pagination,
and other general concerns.

A project-aware reviewer can additionally ask:

``` text
Does this project allow database access directly inside routes?
```

If previous project decisions say that database operations belong in a
service or repository layer, that becomes relevant review context.

The result is not necessarily a longer review. It is a review that can
be more specific to the codebase.

The same idea applies to recurring mistakes.

If previous reviews repeatedly identified missing validation for a
particular API field, that pattern can become useful context when
reviewing another endpoint.

## Results and Behavior

The main behavioral change I was aiming for was consistency.

Without persistent memory, two similar changes can receive similar
generic advice but miss the team's established conventions.

With persistent memory, previous engineering decisions can become part
of the context for future reviews.

For example:

``` text
Previous decision:
Use centralized error handling.

New change:
Adds try/catch logic independently inside every route.

Potential review:
The implementation duplicates error handling that the project
previously centralized. Consider following the existing error-handling
pattern.
```

The value is not that the AI discovered a new programming rule. The
value is that it remembered a project-specific decision.

That distinction is important.

## Lessons I Learned

### 1. Memory needs a purpose

Persistent memory is useful only when the stored information can help
with future tasks. Saving everything creates noise rather than
intelligence.

### 2. Retrieval is as important as storage

A large memory database is not automatically useful. The system needs to
retrieve the small amount of historical context that actually relates to
the current code.

### 3. Project conventions are different from generic best practices

A general rule may be technically reasonable but still conflict with an
existing architecture. A reviewer needs to distinguish between general
knowledge and decisions already made by the project.

### 4. The reviewer should explain why it is making a suggestion

A useful review comment should connect the current code to a concrete
reason. When historical context is involved, that context can make the
explanation easier to understand.

### 5. The system should remain inspectable

When an AI review is wrong, developers need to understand why. Keeping
code analysis, memory retrieval, prompt construction, and review
generation as separate steps makes the system easier to inspect and
improve.

## What I Would Improve Next

The next step would be making memory handling more selective.

Instead of treating every review as equally important, the system could
classify information into categories such as:

-   Coding conventions
-   Architecture decisions
-   Recurring mistakes
-   Security decisions
-   Accepted exceptions
-   Review history

That would make retrieval more targeted.

I would also add stronger review metadata, such as file names, language,
component names, and the type of decision being remembered. This could
improve retrieval quality when a project grows.

Another useful improvement would be allowing developers to explicitly
confirm whether a review decision should become a long-term team rule.
That gives humans control over what becomes persistent knowledge.

## Conclusion

Building a code review agent made me realize that the difficult part of
AI-assisted development is not always generating another answer.

Sometimes the important problem is giving the system enough continuity
to understand why the codebase looks the way it does.

A stateless reviewer can inspect the code in front of it. A memory-aware
reviewer can also take previous engineering decisions into account.

That is where persistent memory becomes useful.

With Hindsight handling the memory layer, the review process can evolve
from:

``` text
Code -> Review
```

toward:

``` text
Past Decisions
      |
      v
Relevant Memory
      |
      v
Current Code -> Review
      |
      v
New Useful Knowledge
      |
      +-------> Future Reviews
```

The result is a code review workflow designed not just to identify
problems, but to preserve the reasoning that helps a team avoid
repeating them.
